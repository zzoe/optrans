# optrans v0.2 增量 PRD

> **文档类型**：增量 PRD（仅描述 v0.1 → v0.2 变更）  
> **作者**：Alice（产品经理）  
> **日期**：2025-06-18  
> **基线版本**：v0.1（二值矩阵 + 全帧渲染 + edition 2021）

---

## 1. 版本目标

v0.2 解决 v0.1 的 **三个核心低效问题**（基于用户对 Horizon H.264 YUV420 视频压缩底层的技术评审）：

| # | 问题 | 根因 | v0.2 方案 |
|---|------|------|-----------|
| 1 | **容量瓶颈**：33 KB/s 太慢 | 仅用亮度通道的 1 bit/模块，浪费 Y 通道精度 | 多级灰度矩阵，每模块承载 2+ bits |
| 2 | **视频冻结**：静止画面导致 Horizon 停止发送帧 | Horizon 检测屏幕无变化后停止编码 | 心跳噪声：注入不可见的动态变化 |
| 3 | **全帧重绘浪费**：每帧渲染 800×800，空间频率高 | 无帧间复用，编码器每帧处理全量数据 | 差分编码：I帧全量 + P帧仅变模块 |

**量化目标**：

| 指标 | v0.1 | v0.2 目标 | 提升倍数 |
|------|------|-----------|----------|
| 每模块比特数 | 1 bit | ≥2 bits (5级灰度) | ≥2× |
| 有效吞吐（含差分） | ~33 KB/s | ~50-60 KB/s | 1.5-2× |
| 静止帧丢失 | 2-3s 后冻结 | 不冻结 | — |

## 3. 编码方案对比与推荐

### 3.1 视频压缩底层约束回顾

```
H.264/H.265 YUV 4:2:0 编码链路：

   RGB 帧 → 显卡/OS → Horizon 采集 → YUV420 转换 → H.264 编码 → 网络 → 解码 → RGB
                                            │
                                   ┌────────┴────────┐
                                   │ Y 通道: 全分辨率  │  ← 亮度保留极好
                                   │ U 通道: 1/4 分辨率│  ← 彩色被严重模糊
                                   │ V 通道: 1/4 分辨率│  ← 量化步长更大
                                   └─────────────────┘
```

**结论**：所有编码信息必须承载在 **Y（亮度）通道**上。灰度 = 纯亮度变化，天然抗压缩。

### 3.2 方案详细评估

#### 方案 A：二值（当前 v0.1）

| 维度 | 评估 |
|------|------|
| 每模块 bit | 1.0 bit |
| 灰度值 | 0（黑）、255（白） |
| 间距 | 255 |
| 抗噪能力 | 极强（阈值 128，容差 ±127） |
| 实现 | 已实现 |
| **结论** | **基线，等待被替代** |

#### 方案 B：4 级灰度（推荐 — 保守选择）

| 维度 | 评估 |
|------|------|
| 每模块 bit | 2.0 bit |
| 灰度值 | 0, 85, 170, 255 |
| 间距 | 85 |
| 抗噪能力 | 强（阈值间隔 42.5，容差 ±42.5） |
| 实现 | 模块值直接映射 2 bits → 灰度 |
| Y 通道噪声 | 典型 ±8~15，间距 85 安全边际 ~3-5× |
| **结论** | **实现最简单，2× 提升，强烈推荐作为首选** |

#### 方案 C：5 级灰度（推荐 — 激进平衡）

| 维度 | 评估 |
|------|------|
| 每模块 bit | ~2.32 bit（log₂5） |
| 灰度值 | 0, 64, 128, 192, 255 |
| 间距 | 64 |
| 抗噪能力 | 较强（阈值间隔 32，容差 ±32） |
| 实现 | 需 5 进制编解码或查表映射（复杂度中） |
| 编码效率 | 每 8 模块编码 1 byte（5⁸=390625 > 2⁸=256），效率 ~97% |
| Y 通道噪声 | 间距 64 相对 ±15 噪声有 ~2× 安全边际 |
| **结论** | **2.3× 提升，安全性可接受，推荐作为默认** |

#### 方案 D：8 级灰度

| 维度 | 评估 |
|------|------|
| 每模块 bit | 3.0 bit |
| 灰度值 | 0, 36, 72, 109, 145, 182, 218, 255 |
| 间距 | ~36 |
| 抗噪能力 | 中（阈值间隔 18，容差 ±18） |
| Y 通道噪声 | 间距 36 vs 噪声 ±15，安全边际仅 ~1.2×，**风险较高** |
| **结论** | **不推荐作为默认，可作为实验选项** |

#### 方案 E：16 级灰度均匀

| 维度 | 评估 |
|------|------|
| 每模块 bit | 4.0 bit |
| 灰度值 | 0, 17, 34, 51, 68, 85, 102, 119, 136, 153, 170, 187, 204, 221, 238, 255 |
| 间距 | 17 |
| 抗噪能力 | 弱（阈值间隔 8.5，容差 ±8.5） |
| Y 通道噪声 | 间距 17 vs 噪声 ±15，**几乎无安全边际** |
| **结论** | **不推荐。在 Horizon 视频压缩条件下几乎必然产生大量误码，RS 纠错压力过大** |

### 3.3 最终推荐

```
┌─────────────────────────────────────────────────────────┐
│  推荐级联方案：5 级灰度 + 差分编码 + 心跳噪声              │
│                                                         │
│  默认参数：                                              │
│  • 编码模式：5 级灰度（gray_levels=5）                    │
│  • 灰度值：0, 64, 128, 192, 255                         │
│  • 差分模式：I+P 帧（默认开启）                           │
│  • 心跳噪声：开启（默认开启）                              │
│                                                         │
│  保守回退：--gray-levels 4（4 级灰度，2× 提升）           │
│  最大兼容：--gray-levels 2 --no-diff（退回 v0.1 行为）    │
└─────────────────────────────────────────────────────────┘
```

**不推荐 8/16 级灰度的核心原因**：Horizon H.264 量化参数（QP）在 Y 通道上的典型步长对应 ±10~20 的像素值波动。16 级灰度的 17 间距在此条件下误码率不可接受。若未来切换到无损编码（如 H.265 lossless），可重新评估。

### 3.4 灰度编码方案（5 级灰度）

**编码规则**（每模块 2.32 bit）：

```
灰度值 → 逻辑值（用于解码）：
  0   (接近黑)  → 0b000
  64  (深灰)    → 0b001
  128 (中灰)    → 0b010
  192 (浅灰)    → 0b011
  255 (白)      → 0b100

解码阈值（中点）：
  0~31   → 0   (黑)
  32~95  → 64  (深灰)
  96~159 → 128 (中灰)
  160~223→ 192 (浅灰)
  224~255→ 255 (白)
```

**数据打包**：5 进制编码。每 8 个模块一组，编码为 3 bytes（5⁸ = 390625 < 2²⁴ = 16777216）。编码效率 = 24 bits / 8 modules = 3 bits/module（实际有效 ~2.32 bits/module，差额为编码开销）。

**Finder Pattern 和格式信息区保持二值**（黑白），仅数据矩阵使用灰度。确保帧定位和格式解码的可靠性不受灰度噪声影响。

## 4. 心跳噪声方案

### 4.1 原理

Horizon 在检测到屏幕内容静止 2-3 秒后停止发送视频帧（冻结优化）。需要在画面中注入**周期性的微量变化**，使编码器判定画面持续活动。

### 4.2 具体方案

```
位置：窗口右下角，数据矩阵区域之外（模块坐标 N-3, N-3 起始的 2×2 像素块）

实现：
┌──────────────────────────────────────────┐
│                                          │
│   数据矩阵区域                             │
│                                          │
│                               ┌──┐       │
│                               │██│ ← 2×2 │
│                               └──┘  像素块│
└──────────────────────────────────────────┘
  窗口 800×800（右下角 2×2 像素）

变化规则：
- 2×2 像素块的值按帧序列号循环：
  frame_seq % 4 == 0 → (128, 128, 128, 128)  中灰
  frame_seq % 4 == 1 → (129, 129, 129, 129)  中灰+1
  frame_seq % 4 == 2 → (128, 128, 128, 128)  中灰
  frame_seq % 4 == 3 → (127, 127, 127, 127)  中灰-1

- 变化幅度 ±1，人眼完全无法察觉（在 800×800 画面底角）
- 但编码器能检测到像素变化，维持视频流活跃
```

### 4.3 设计约束

| 约束 | 值 | 说明 |
|------|-----|------|
| 位置 | 窗口右下角 (N-3, N-3) 起始 | 不侵占数据矩阵（finder pattern 左下角占 7×7，行 N-7 起） |
| 尺寸 | 2×2 像素 | 最小可检测变化单元 |
| 变化幅度 | ±1 灰度值 | 远低于人眼感知阈值（JND ~3-5） |
| 变化频率 | 每帧变化 | 与帧率同步，确保每帧都有变化 |
| 对解码影响 | 零 | 不在数据矩阵区域内 |

### 4.4 实现位置

`encoder/render.rs` 的 `render_frame()` 函数，在像素缓冲区构建完成后、返回前，根据 `frame_sequence` 修改心跳像素。

## 5. 差分编码方案（I+P 帧）

### 5.1 核心思路

v0.1 每帧全量渲染所有模块。在 Horizon 编码端，这意味每帧都是高空间频率的完整画面——编码器必须为每个宏块分配比特。

v0.2 改为：
- **I 帧（Intra）**：完整渲染所有模块（同 v0.1 行为），作为基准帧
- **P 帧（Differential）**：仅渲染**与上一帧不同的模块**，其余模块填充为背景色（如 128 中灰），使编码器将这些区域识别为"无变化"，分配极少比特

### 5.2 帧格式变更

#### FormatInfo 字段变更

利用 `reserved` 字段的 2 bits：

```
reserved: 2 bits
  bit 0: frame_kind    — 0 = I-frame, 1 = P-frame
  bit 1: encoding_mode — 0 = binary (v0.1 兼容), 1 = grayscale
```

> **向后兼容说明**：v0.1 中 reserved 恒为 0，即 (frame_kind=0=I-frame, encoding_mode=0=binary)。v0.2 接收端检测到 reserved=0 → 按 v0.1 二值 I 帧解码。v0.1 接收端遇到 reserved≠0 → CRC 校验失败（因为 reserved 参与了 CRC 计算），会丢弃该帧。这是预期行为——v0.1 接收端不兼容 v0.2 灰度帧。

#### P 帧载荷格式

P 帧的 payload 与 I 帧不同：

```
I 帧 payload（与 v0.1 相同）：
  [block_index: 4B LE] + [block_data: N bytes]

P 帧 payload：
  [base_frame_seq: 2B LE] + [module_count: 2B LE] + [module_entries...]
  
  每个 module_entry：
    [module_index: 2B LE] + [module_value: 1B]
    
  module_index: 数据矩阵中的行优先序号（0-based）
  module_value: 灰度值（0-255）
```

**P 帧渲染**：
- 先将数据矩阵区域全部填充为背景色（128 中灰）
- 按 module_entries 逐个渲染变化的模块
- Finder pattern 和格式信息区保持不变（始终全量渲染，确保定位）

### 5.3 I/P 帧决策策略

```
发送端策略（初始简化版）：
  • 第 1 帧：I 帧（元数据帧）
  • 每轮循环的第 1 个数据帧：I 帧
  • 每 N 个连续 P 帧后：强制刷新一个 I 帧（N 可配置，默认 10）
  • 其余数据帧：P 帧

  I 帧间隔过大会导致误差累积，过小则差分收益降低。
  默认 N=10 是平衡点：90% 的帧为 P 帧，大幅降低平均数据密度。
```

### 5.4 兼容性矩阵

| 发送端 | 接收端 | 结果 |
|--------|--------|------|
| v0.1 | v0.1 | ✅ 正常 |
| v0.1 | v0.2 | ✅ v0.2 检测 reserved=0 → 二值模式 |
| v0.2 (binary) | v0.1 | ✅ reserved=0 |
| v0.2 (gray) | v0.1 | ❌ 格式信息 CRC 失败（预期） |
| v0.2 (binary) | v0.2 | ✅ |
| v0.2 (gray) | v0.2 | ✅ |

### 7.2 Edition 2024 注意事项

Rust 2024 edition 的关键变更（可能影响 optrans）：

| 变更 | 影响 | 处理 |
|------|------|------|
| `gen` 成为关键字 | 如有变量名 `gen` 需重命名 | 代码审查 |
| `unsafe` 块内 `unsafe` 不再需要 | 简化 win32 FFI 代码 | 自动修复 |
| RPIT lifetime capture | 可能影响返回 `impl Trait` 的函数 | 检查编译警告 |
| `!` type 改进 | 不影响 | — |

操作步骤：
1. 修改 `Cargo.toml` edition = `"2024"`
2. `cargo update` 拉取所有依赖最新版
3. `cargo fix --edition` 自动迁移
4. `cargo build` 验证
